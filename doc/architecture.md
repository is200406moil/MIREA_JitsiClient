# Устройство приложения

## Общая схема

Приложение состоит из двух частей:

- **Экраны вне встречи** — QML (Sailfish Silica): главный экран с вкладками «Недавние», «Календарь», «Настройки», профиль, выбор языка, экран перед входом, обложка.
- **Экран встречи** — собственный клиент на [lib-jitsi-meet](https://github.com/jitsi/lib-jitsi-meet) (`qml/call`: `index.html`, `call.js`, `call.css`), открытый в Aurora WebView (Chromium). Медиа идёт через WebRTC встроенного браузера.

Библиотека lib-jitsi-meet и `config.js` загружаются с того сервера Jitsi, к которому идёт подключение, поэтому версия клиента всегда совпадает с сервером. Интерфейс встречи повторяет мобильный Jitsi Meet; тексты — из языковых файлов Jitsi (`qml/call/lang`).

## Локальный сервер и мост

`AppState` (`src/appstate.*`) поднимает HTTP-сервер на `127.0.0.1` со случайным портом и отдаёт страницу встречи по случайному пути для каждой встречи. Настройки встречи (сервер, комната, имя, состояние камеры и микрофона, сохранённый логин) подставляются в страницу.

- **Страница → приложение:** запросы `POST <путь>/event` с именем события и данными (`left`, `token`, `credentials`, `callState`, `moderation`, `openSettings` и др.). `RoomPage.qml` обрабатывает их в `onConferenceEvent`.
- **Приложение → страница:** `webView.runJavaScript("window.auroraCall.…")` — выход, переключение микрофона, установка токена, параметры модератора.

Журнал встречи пишется в `~/.cache/ru.mirea/JitsiClient/call.log`.

## Вход на защищённые серверы

- **Логин и пароль (Prosody internal):** окно «Войти» как в Jitsi; при ожидании организатора повторная попытка входа каждые 5 с.
- **Токен организатора (JWT):** страница `tokenAuthUrl` сервера открывается во встроенном браузере (`OrganizerLoginPage.qml`), возврат с `#jwt=` перехватывается.

Принятые сервером логин, пароль, токен и ключ трансляции сохраняются по адресу сервера в `KeystoreLoginStore` (`src/keystoreloginstore.*`):

- файл `logins.dat` в каталоге данных приложения (права только владельца), внутри — JSON с записями по серверам, зашифрованный AES-256-GCM (QCA, провайдер `qca-ossl`);
- ключ шифрования вычисляется в [Aurora Keystore](https://developer.auroraos.ru/doc/platform/tee) (`src/keystorekey.*`): HMAC-SHA256 от постоянного сообщения неизвлекаемым ключом 48 байт в токене USERAPP через плагин `qca-aurora-pkcs11`, как в [примере ОМП](https://gitlab.com/omprussia/demos/KeyStore). Ключ есть только в памяти приложения, на диске и в аргументах других программ его нет;
- отклонённые сервером данные удаляются; запись идёт через `QSaveFile`.

Если Keystore недоступен (в том числе в эмуляторе: в его ядре нет `CONFIG_CUSE`, служба `softhsm-cused` не запускается), логины хранятся только в памяти до закрытия приложения, файл не трогается, причина пишется в журнал встречи. Файл, который ключ из хранилища не расшифровывает, заменяется при следующем сохранении. Разрешение `Keystore` в `.desktop` указывать нельзя: пакет с ним не устанавливается. Ключ трансляции попадает на страницу только своего сервера.

Системный криптоконтейнер `sstore` не используется: служба передаёт пароль контейнера программе securefs в командной строке, и он попадает в системный журнал.

## Работа в фоне

- **`Nemo.KeepAlive`** в `RoomPage.qml` не даёт системе засыпать, пока открыт экран встречи. Звук передаётся при заблокированном экране и в свёрнутом приложении.
- **Уведомление встречи** (`src/callcontrol.*`) публикуется напрямую в `org.freedesktop.Notifications`:
  - подсказки `x-nemo-user-removable=false` (не удаляется «Очистить все»), `resident=true` (остаётся после кнопок), `suppress-sound=true`;
  - кнопки «Микрофон» и «Выход» и нажатие на уведомление — через `x-nemo-remote-action-*`, вызывающие объект `/call` приложения на сессионной шине. Аврора разрешает действиям вызывать только имя, совпадающее с id приложения (`ru.mirea.JitsiClient`);
  - подсказку `urgency` передавать нельзя: экран «События» отбрасывает уведомление с ней как некорректное;
  - уведомление обновляется на месте по своему id. Пользователь не может его удалить, поэтому у него есть срок жизни 60 с, и приложение продлевает его каждые 20 с. Если приложение аварийно завершилось, уведомление исчезает само; оболочка после перезапуска его тоже не восстанавливает;
  - при запуске приложение закрывает оставшиеся уведомления прошлого запуска: по номеру из файла `notification.id` и по списку `GetNotifications`.
- **Обложка** (`qml/cover/DefaultCoverPage.qml`): во время встречи — комната, время и действия «микрофон» и «выход», вне встречи — вкладки главного экрана.

## Показ экрана

StreamCamera — общий API камер Авроры с плагинами для разных источников: обычные камеры (`streamcamera-gstreamer-camera`, через неё камеру получает и Chromium) и экран (`screengrab`, камера с `CameraFacing::Screen`).

Aurora WebView не умеет `getDisplayMedia`, поэтому экран захватывает приложение: `ScreenCapture` (`src/screencapture.*`) открывает камеру StreamCamera с `CameraFacing::Screen` (разрешение `ScreenCapture`) и отдаёт кадры JPEG по адресу `<путь>/screen.jpg`. Страница рисует их на canvas и передаёт поток `canvas.captureStream()` как дорожку показа экрана. Если кадров нет 8 секунд, показывается ошибка Jitsi «не удалось начать показ экрана».

## Камера в эмуляторе

Chromium получает камеру через StreamCamera, а камера эмулятора доступна только как элемент GStreamer `emulatorcambin`. Адаптер `emulator/emulator-provider.cpp` регистрирует его как камеру для StreamCamera. Адаптер и нужные библиотеки GStreamer входят только в сборку x86_64 (приватный каталог `/usr/share/ru.mirea.JitsiClient/lib`) и включаются в `main.cpp`, только если найден источник камеры эмулятора. На устройстве используется штатная камера.

## Хранение данных

- Настройки, профиль и комнаты — база SQLite `~/.local/share/ru.mirea/JitsiClient/jitsi.db` (класс `Storage`, `src/storage.*`):
  - таблица `settings` (`key`, `value`) — настройки и профиль;
  - таблица `rooms` (`id`, `name`, `server`, `last_used`, `duration`) — комнаты; `id` — SHA-256 от адреса сервера и названия, `duration` пуст до конца первой встречи;
  - версия схемы — `PRAGMA user_version`;
  - данные прежних версий из `QSettings` переносятся при первом запуске одной транзакцией, после чего группа `client` удаляется.
- Логины, токены и ключи трансляции — `logins.dat`, зашифрованный ключом из Keystore (см. выше).
- Кэш WebView и журнал встречи — `~/.cache/ru.mirea/JitsiClient/`.

## Доверие к коду сервера

Страница встречи выполняет код с сервера Jitsi (`lib-jitsi-meet`, `config.js`), поэтому события страницы не считаются действиями пользователя. Захват экрана запускается только после ответа в окне приложения (`AppState::answerScreenShare`), а кадры `screen.jpg` отдаются только после согласия. Камера и микрофон для страницы встречи разрешаются автоматически, как и раньше: от кода сервера это не защищает.
