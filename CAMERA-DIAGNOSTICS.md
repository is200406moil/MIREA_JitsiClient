# Камера в эмуляторе Aurora OS

28 октября 2026. Проверенная среда: Windows, Aurora SDK / OS 5.2.1.200,
эмулятор x86_64, Chromium 126.

## Причина

Qt получал поток камеры компьютера через `emulatorcambin`, однако Chromium
использует StreamCamera. Источник эмулятора не был зарегистрирован как
GstDeviceProvider, поэтому WebRTC и Jitsi сообщали об отсутствии камеры.
Это воспроизводилось в отдельном локальном WebView без Jitsi и авторизации.

## Исправление

`emulator/emulator-provider.cpp` регистрирует настоящий источник эмулятора
для StreamCamera. Свойство `facing=2` преобразуется в переднюю камеру:
источник с неизвестным положением Chromium пропускал. `videoconvert`,
`videoscale` и `videorate` согласуют I420, 640×480, 30 кадров/с.
Последнее необходимо, поскольку входной RTP/JPEG-поток объявлял частоту 0/1.
Тестовые изображения и фиктивные камеры в клиент не включены.

Адаптер и необходимые библиотеки включены в приватный каталог приложения
`/usr/share/ru.vkr.JitsiAuroraPrototype/lib`. RPM использует документированную
модель приватных библиотек Авроры: зависимости исключаются из метаданных
только для библиотек, действительно поставляемых внутри приложения.
Установка системного адаптера и системный сертификат не нужны.

На x86_64 при наличии `libgstemulatorcamsrc.so` перед инициализацией WebView:

- `GST_PLUGIN_PATH` указывает на приватный адаптер;
- `GST_PLUGIN_SYSTEM_PATH_1_0` сохраняет поиск штатных модулей в
  `/usr/lib64/gstreamer-1.0`: после переноса GStreamer в приложение его
  автоматический поиск иначе смещался к приватному каталогу;
- `STREAMCAMERA_PLUGIN_DIR` выбирает поставляемые camera/codec-модули;
- `GSTREAMER_CAMERA_DEVICE_PROVIDER` выбирает адаптер эмулятора.

На физическом устройстве этот код не активируется: используется штатный
механизм камер устройства. Его необходимо проверить отдельно.

## Полученные результаты

- Нативный Qt: настоящий кадр 640×480.
- Прямой GStreamer: настоящий I420-кадр из `emulatorcambin`.
- Локальный WebRTC-тест `tests/webcam-probe.cpp`: videoInput=1,
  audioInput=2, 640×480, 30 последовательных обратных вызовов видеокадра.
  Два последовательных запуска завершились успешно. Изображения не сохраняются.
- Установленный клиент 0.1-15, в обычной среде приложения с диагностическим
  указанием системного каталога модулей: Jitsi сообщил `cameras=1,
  microphones=2`; живое изображение видно внутри комнаты.
- В 0.1-16 указание каталога закреплено в исходниках. После обычного
  запуска без диагностических переменных подтверждено живое изображение
  внутри Jitsi, с выключенным микрофоном.
- После изменения интерфейса регрессионная проверка 0.1-20 также показала
  живое видео при обычном запуске, с выключенным микрофоном.
- В 0.1-24 виден живой предпросмотр до входа; после освобождения камеры
  встроенная встреча получает её и показывает видео. Проверено при обычном
  запуске приложения в эмуляторе.

Подпись обычным ключом SDK прошла проверку. Сборка 0.1-16 установилась
через стандартное развёртывание с сохранением пользовательских данных.
Проверки подписей, разрешения и системные политики не изменялись.
Текущая сборка 0.1-24 также подписана обычным ключом SDK и установлена
с сохранением пользовательских данных. Отдельный системный RPM не нужен.

## Настройка передачи

В Aurora IDE: Инструменты → ОС Аврора → Управление эмуляцией → Камера.
Выбрать камеру компьютера, 640×480, 30 кадров/с, установить настройки
и запустить передачу. После перезапуска эмулятора проверить её снова.
Сканер QR подтверждает доступность камеры в Qt, но сам по себе
не проверяет путь StreamCamera → Chromium → WebRTC.

## Границы проверки

Полный звонок с двумя участниками, длительная работа и блокировка экрана
ещё не проверены. Публичная комната meet.jit.si ожидает входа организатора.
SDK-источник выдаёт предупреждения при освобождении внутренних объектов;
их влияние на длительную работу следует проверить отдельно.
